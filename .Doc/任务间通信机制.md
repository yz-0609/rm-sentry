1. ## 1) 机制定位（它解决什么问题）

   它用“话题（topic）”做中介，让任务之间不直接互相包含头文件、也不直接访问彼此内部数据，从而解耦。
   在这个项目里，主要是 `robot_cmd / chassis / gimbal / shoot` 这些应用通过 topic 交换“控制指令”和“状态反馈”。

   ------

   ## 2) 核心模型

   - **Publisher（发布者）**：向某个 topic 推送消息
   - **Subscriber（订阅者）**：从某个 topic 拉取消息
   - **Topic（话题）**：字符串命名，如 `"gimbal_cmd"`、`"chassis_feed"`

   对外接口只有 4 个：

   - `PubRegister(name, data_len)`
   - `SubRegister(name, data_len)`
   - `PubPushMessage(pub, data_ptr)`
   - `SubGetMessage(sub, data_ptr)`

   ------

   ## 3) 内部数据结构（实现方式）

   ### 3.1 话题组织：发布者链表

   消息中心内部维护一个“哑头结点 + Publisher 链表”（`message_center`）。
   每个 Publisher 节点对应一个 topic，记录：

   - topic 名
   - 该 topic 消息长度 `data_len`
   - 该 topic 下订阅者链表头 `first_subs`

   ### 3.2 订阅者组织：每个 topic 一条订阅者链表

   每个 Subscriber 结构体里有：

   - 一个固定长度队列 `queue[QUEUE_SIZE]`（元素是 `void*`，每个元素单独 `malloc(data_len)`）
   - `front_idx / back_idx / temp_size`（环形队列索引和当前长度）
   - `next_subs_queue`（挂到同 topic 的下一个订阅者）

   ------

   ## 4) 注册和收发流程

   ### 4.1 注册

   - `PubRegister`：查找是否已有同名 topic；有则复用，无则新建 Publisher 节点。
   - `SubRegister`：内部会先调用 `PubRegister`，确保 topic 存在；再创建 Subscriber 并挂到该 topic 的订阅者链表尾部。

   ### 4.2 发布（`PubPushMessage`）

   发布者遍历该 topic 下所有订阅者，把数据 `memcpy` 到每个订阅者自己的队列里。
   若队列满了，先丢最旧消息，再写新消息（覆盖策略）。

   ### 4.3 订阅读取（`SubGetMessage`）

   订阅者从自己队列头读一条消息到 `data_ptr`，成功返回 `1`；队列空返回 `0`。

   ------

   这套项目里 `RobotTask()`（5ms 周期）内部顺序调用： `RobotCMDTask -> GimbalTask -> ShootTask -> ChassisTask`。
   也就是说这些应用逻辑在同一任务上下文里串行执行，因此这个消息中心不依赖锁也能工作。

   ------

   ## 7) 当前实现特点与限制

   - `QUEUE_SIZE` 默认是 `1`：本质更像“最新值同步”，不是长队列缓存。
   - 相同 topic 必须使用相同 `data_len`，否则会报错并停机。
   - 基于 `malloc` 动态分配，初始化后常驻，不提供释放。
   - 线程安全机制（mutex）未实现；当前依赖调用场景（主要在 RobotTask 串行执行）。
   - 文档里也明确是“伪 pubsub / 轻量实现”。





你这个卡点很正常，这套实现是**两层链表**，抓住这点就通了：

## 1）第一层链表：话题链表（Publisher 链表）

在 `/home/runner/work/rm-sentry/rm-sentry/modules/message_center/message_center.c` 里有个哑头结点：

- `static Publisher_t message_center`（不是实际话题，只是链表头）

每个 `Publisher_t` 节点代表一个 topic，关键指针是：

- `next_topic_node`：指向下一个 topic（第一层链表）
- `first_subs`：指向该 topic 的第一个订阅者（第二层链表入口）

所以结构是：
`message_center -> topicA -> topicB -> topicC -> ...`

------

## 2）第二层链表：某个 topic 下的订阅者链表

每个 `Subscriber_t` 有：

- `next_subs_queue`：指向**同一 topic**的下一个订阅者

所以某个 topic 内部是：
`topicA.first_subs -> sub1 -> sub2 -> sub3 -> ...`

------

## 3）注册时链表怎么连

### `PubRegister(name, data_len)`

流程：

1. 从 `message_center` 开始遍历 `next_topic_node`
2. 找到同名 topic 就返回
3. 找不到就在链表尾部 `malloc` 一个新的 `Publisher_t`，挂到尾巴

> 这就是第一层链表的“查找/尾插”。

### `SubRegister(name, data_len)`

流程：

1. 先调用 `PubRegister`，确保 topic 存在
2. 新建一个 `Subscriber_t`
3. 如果 `pub->first_subs == NULL`，它就是第一个订阅者
4. 否则遍历 `next_subs_queue` 到尾部，再挂上去

> 这就是第二层链表的“查找/尾插”。

------

## 4）发布时链表怎么用

`PubPushMessage(pub, data_ptr)`：

1. 从 `pub->first_subs` 开始
2. 沿着 `next_subs_queue` 遍历每个订阅者
3. 把消息复制进每个订阅者自己的队列
4. `iter = iter->next_subs_queue` 直到 `NULL`

也就是：**一个 topic 广播给它的订阅者链表**。
