# RM2027 下位机向上位机上传数据改动方案

日期：2026-10-30。状态：第 4、5 节的上传适配已实施，未启用包仍保持关闭；表中“当前”指改动前的接口基线。

本文仅根据当前下位机 USB 上传接口制定新赛季适配方案，不涉及上位机下发控制指令。目标是保留已有帧封装、包 ID、发送开关和能够继续使用的数据布局，仅修改失效的数据来源及确实需要变化的字段。

兵种口径以 2027 通信协议为准：`1/101` 为红/蓝方重装机器人，`2/102` 为保留位。原英雄、工程相关字段通过重装语义和保留占位适配，不将后面的机器人编号前移。协议附录仍列出 `5/105`，但 `0x0003`、`0x020B` 没有提供该兵种对应槽位的数据；不能据此把所有协议中的 5 号机器人都删除。

## 1. 最小改动范围

建议首轮只修改上传结构定义和发送函数所在的两个源码文件，保持现有上传调用顺序及开关：

| 当前已启用的 USB 上传包 | 首轮处理 |
| --- | --- |
| `0x02` IMU | 不改字段、长度和单位 |
| `0x07` 比赛状态 | 不改字段和长度 |
| `0x0A` RFID | 将旧 20 个布尔字段替换为新协议的两个原始状态字段，共 6 字节 |
| `0x0B` 本机状态 | 保留原 29 字节业务数据，仅修正伤害原因的取值成员 |

血量 `0x06`、地面位置 `0x09`、增益 `0x0D` 的发送调用目前被注释，但函数体仍参与编译，引用已删除裁判字段的地方也必须修正。修正这些函数不代表自动开启发送。

事件 `0x04`、哨兵反馈 `0x0E` 保持关闭；本轮不为它们增加尚未使用的数据。新赛季新增的血量差、双方控制度、命中坐标、弹速上限、姿态计时等，不自动加入现有上传包，按第 8 节在确有使用需求时扩展。

这里的“最小改动”包括保留旧 USB 占位空间：不为了让上传结构体与裁判结构体完全相同而缩短血量包或地面位置包。RFID 需要重新定义；增益包需要修正位宽，这两处应与接收端同步升级。

## 2. 保留现有 USB 帧封装

当前默认启用 `VISION_USE_VCP`，以 `UsbSendData()` 实际调用的 USB CDC 上传为依据。现有 Seasky 串口协议文档描述的是另一套 `0xA5` 帧，不能用来计算本 USB 接口的包长。

| 整帧字节偏移 | 字段 | 字节数 | 约定 |
| --- | --- | ---: | --- |
| 0 | `frame_header.sof` | 1 | 固定 `0x5A` |
| 1 | `frame_header.len` | 1 | 时间戳与业务数据的合计长度 |
| 2 | `frame_header.id` | 1 | 保留现有 USB 包 ID |
| 3 | `frame_header.crc` | 1 | 前 3 字节的 CRC8 |
| 4 | `time_stamp` | 4 | 保留当前 `uint32_t` 毫秒时间戳 |
| 8 | `data` | D | 本文下述业务数据 |
| 8 + D | `crc` | 2 | 帧头、时间戳和业务数据的 CRC16 |

长度计算继续使用现有约定：

```text
frame_header.len = 4 + D = sizeof(上传包结构体) - 6
完整帧长度       = 10 + D = frame_header.len + 6
```

多字节整数、浮点字段继续按 STM32 当前的小端布局发送。业务数据偏移均从 `data` 开始计算，换算整帧偏移时加 8。USB 包 ID 与裁判系统 `cmd_id` 是两个不同的编号空间。

下表“当前”大小已用当前工程头文件及 ARM GCC 核验，包含内层结构体实际产生的填充。

| USB ID | 内容 | 当前发送 | 业务数据 D：当前 → 方案 | `len`：当前 → 方案 | 完整帧：当前 → 方案 |
| --- | --- | --- | --- | --- | --- |
| `0x02` | IMU | 开启 | 24 → 24 | 28 → 28 | 34 → 34 |
| `0x07` | 比赛状态 | 开启 | 3 → 3 | 7 → 7 | 13 → 13 |
| `0x0A` | RFID | 开启 | **20 → 6** | **24 → 10** | **30 → 16** |
| `0x0B` | 本机状态 | 开启 | 29 → 29 | 33 → 33 | 39 → 39 |
| `0x06` | 血量 | 关闭 | 16 → 16 | 20 → 20 | 26 → 26 |
| `0x09` | 地面位置 | 关闭 | **48 → 48** | 52 → 52 | 58 → 58 |
| `0x0D` | 增益 | 关闭 | **7 → 7，字段偏移变化** | 11 → 11 | 17 → 17 |

| `0x0E` | 哨兵反馈 | 关闭 | **8 → 8，本轮不扩展** | 12 → 12 | 18 → 18 |

`0x08` 底盘运动、`0x0C` 云台状态，以及其他调试/硬件状态上传包不因本次裁判协议适配改变。地面位置的真实 USB ID 是宏定义中的 `0x09`，不是结构体旁旧注释写的 `0x08`。

## 4. 已启用上传包的改动

### 4.1 `0x0A` RFID：直接上传两个原始状态字段

现有 `SendDataRfidStatus_s.data` 是 20 个独立 `bool`，实际占 20 字节。其场地名称与位号映射已经不适用于 2027。建议仅替换该包的业务数据为：

```c
struct
{
    uint32_t rfid_status;
    uint16_t rfid_status_2;
} __packed__ data;
```

保留外层 `FrameHeader_t`、`time_stamp`、CRC 及包 ID。发送函数只需要从裁判缓存复制两个字段：

```c
SEND_RFID_STATUS_DATA.data.rfid_status = refer_data->RFIDStatus.rfid_status;
SEND_RFID_STATUS_DATA.data.rfid_status_2 = refer_data->RFIDStatus.rfid_status_2;
```

| 业务偏移 | 字段 | 类型 | 字节数 | 数据来源 |
| --- | --- | --- | ---: | --- |
| 0 | `rfid_status` | `uint32_t` | 4 | 裁判 `0x0209`，偏移 0 |
| 4 | `rfid_status_2` | `uint16_t` | 2 | 裁判 `0x0209`，偏移 4 |

接收端按位解释，保持裁判协议的 R/B 场地名称，避免下位机再次将 R/B 误映射为己方/对方。

| `rfid_status` 位号 | 新赛季含义 |
| --- | --- |
| 0 | 己方补给区 |
| 1 | 己方装配区增益点 |
| 2 / 3 | R / B 基地增益点 |
| 4 / 5 | R / B 堡垒增益点 |
| 6 / 7 | R / B 中央高地增益点 |
| 8 / 9 | R / B 前哨增益点 |
| 10 | 己方制高点增益点 |
| 11 / 12 / 13 | R 高地 / B 高地 / 中央控制区，仅 RMUL |
| 14 / 15 | 己方中央高地下方 / 上方地形跨越点 |
| 16 / 17 | 对方中央高地下方 / 上方地形跨越点 |
| 18 / 19 | 己方公路下方 / 上方地形跨越点 |
| 20 / 21 | 对方公路下方 / 上方地形跨越点 |
| 22～24 | 己方公路一侧隧道，下方 / 中间 / 上方 |
| 25～27 | 靠中央高地、靠己方梯形高地的隧道，较低 / 中间 / 较高 |
| 28～30 | 远离中央高地的隧道，距己方梯形高地较远 / 中间 / 较近 |
| 31 | 本版未定义，接收端不赋予业务含义 |

| `rfid_status_2` 位号 | 新赛季含义 |
| --- | --- |
| 0～2 | 对方公路一侧隧道，下方 / 中间 / 上方 |
| 3～5 | 靠中央高地、靠对方梯形高地的隧道，较低 / 中间 / 较高 |
| 6～8 | 远离中央高地的隧道，距对方梯形高地较远 / 中间 / 较近 |
| 9～15 | 本版未定义，接收端不赋予业务含义 |

位值 `1` 表示检测到对应 RFID 卡，`0` 表示未检测到。赛外这些状态为 0，不能将赛外全 0 单独解释为模块故障。

接收端最小同步：将 `0x0A` 业务数据读取长度从 20 改为 6，`len` 从 24 改为 10，替换旧布尔字段解析。不再沿用“bit 0 是己方基地”“bit 19/20 是补血点”等旧映射。

### 4.2 `0x0B` 本机状态：保持 29 字节布局

已有字段继续上传，只修正伤害原因取值：

```c
SEND_ROBOT_STATUS_DATA.data.hp_deduction_reason =
    refer_data->RobotHurt.HP_deduction_reason;
```

旧成员 `refer_data->RobotHurt.hurt_type` 已不存在。当前 USB 成员 `current_up` 名称虽不准确，首轮保留以减少源码改动，其含义仍为当前血量。

| 业务偏移 | 上传字段 | 类型 / 字节数 | 新赛季处理 |
| --- | --- | --- | --- |
| 0 | `robot_id` | `uint8_t` / 1 | 原值上传；1/101 表示重装，2/102 为保留，0 为尚无有效身份 |
| 1 | `robot_level` | `uint8_t` / 1 | 保留 |
| 2 | `current_up` | `uint16_t` / 2 | 来源 `GameRobotState.current_HP` |
| 4 | `maximum_hp` | `uint16_t` / 2 | 保留 |
| 6 | `shooter_barrel_cooling_value` | `uint16_t` / 2 | 保留基础冷却值 |
| 8 | `shooter_barrel_heat_limit` | `uint16_t` / 2 | 保留热量上限 |
| 10 | `shooter_17mm_1_barrel_heat` | `uint16_t` / 2 | 来源 `PowerHeatData.shooter_17mm_barrel_heat` |
| 12 | `robot_pos_x` | `float` / 4 | 保留，单位 m |
| 16 | `robot_pos_y` | `float` / 4 | 保留，单位 m |
| 20 | `robot_pos_angle` | `float` / 4 | 保留裁判位置消息的角度值，单位度，不改成 IMU 弧度 |
| 24 | `armor_id` + `hp_deduction_reason` | 各 4 bit，合计 1 | 低 4 位装甲 ID，高 4 位伤害原因 |
| 25 | `projectile_allowance_17mm` | `uint16_t` / 2 | 保留 |
| 27 | `remaining_gold_coin` | `uint16_t` / 2 | 保留 |

伤害原因按新协议解释：0 为弹丸攻击、1 为装甲模块离线、2 为超级电容管理模块离线、5 为撞击。未列出的值不要套用旧赛季原因表。

首轮不把 `bullet_speed_limit`、命中序号、命中坐标等追加到这个包，避免改变当前正在使用的自瞄/导航状态接口。

## 5. 未启用函数的必要适配

以下包保持关闭，但其发送函数需要消除失效成员引用，保证后续代码能够编译。除 `0x0D` 的位宽修正外，保留当前 USB 布局。

### 5.1 `0x06` 血量：保留 16 字节及现有槽位

首轮仍使用现有 `SendDataAllRobotHp_s.data`，不整包复制新的 24 字节裁判结构体。

| 业务偏移 | 现有 USB 字段 | 首轮取值 / 含义 |
| --- | --- | --- |
| 0 | `ally_1_robot_HP` | `GameRobotHP.ally_1_robot_HP`；己方重装血量 |
| 2 | `ally_2_robot_HP` | 固定填 0，作为保留槽，不再表示工程机器人血量 |
| 4 | `ally_3_robot_HP` | 同名裁判字段 |
| 6 | `ally_4_robot_HP` | 同名裁判字段 |
| 8 | `reserved` | 固定填 0，不悄悄改成有符号伤害差 |
| 10 | `ally_7_robot_HP` | 同名裁判字段 |
| 12 | `ally_outpost_HP` | 开局己方一侧前哨的血量，按下述规则取值 |
| 14 | `ally_base_HP` | 同名裁判字段 |

对本哨兵工程，`robot_id == 7` 时，`ally_outpost_HP` 取 `outpost_R_HP`；`robot_id == 107` 时取 `outpost_B_HP`；身份尚未有效时填 0。这里保留的是“开局己方一侧前哨”含义，不表示当前由己方控制的前哨。R/B 前哨身份不会随阵地控制状态改变。

不得再读取已删除的 `GameRobotHP.ally_2_robot_HP` 或 `GameRobotHP.ally_outpost_HP`。本轮不上传新增 `damage_difference`、另一侧前哨、敌方基地和双方控制度；需要这些数据时再按第 8 节扩展。

### 5.2 `0x09` 地面位置：保留当前 48 字节布局

当前 USB 结构体共有 12 个 `float`，是 **48 字节**；裁判 `0x020B` 是 40 字节。两者不能直接等长 `memcpy`。为保留接收端偏移，首轮只调整逐字段赋值：

| 业务偏移 | 现有 USB 字段 | 首轮取值 / 新赛季含义 |
| --- | --- | --- |
| 0 / 4 | `hero_x` / `hero_y` | 来源 `GroundRobotPos.heavyengineer_x/y`，含义改为己方重装坐标 |
| 8 / 12 | `engineer_x` / `engineer_y` | 固定填 `0.0f`，保留原工程槽位 |
| 16 / 20 | `standard_3_x` / `standard_3_y` | 同名裁判字段 |
| 24 / 28 | `standard_4_x` / `standard_4_y` | 同名裁判字段 |
| 32 / 36 | `standard_5_x` / `standard_5_y` | 固定填 `0.0f`，本条裁判消息未提供 5 号坐标 |
| 40 / 44 | `reserved1` / `reserved2` | 固定填 `0.0f`，保留 USB 原有尾部占位 |

旧 USB 成员名 `hero_x/y` 可以先作为兼容名称保留，接收端必须按重装坐标使用，后续统一重命名为 `heavyengineer_x/y` 不会改变字节布局。位置单位和裁判场地坐标系保持原值，不进行红蓝翻转。

不得再从裁判缓存读取已删除的 `hero_x/y`、`engineer_x/y`、`reserved1/2`。保留位直接置零，不把裁判缓存中未定义的保留数据映射为有效坐标。接收端不能仅以 `(0, 0)` 区分“未提供坐标”和“机器人位于原点”；本方案不增加有效性标志，保留槽固定按未提供处理。

### 5.3 `0x0D` 增益：修正冷却增益位宽，业务长度仍为 7

旧上传字段 `cooling_buff` 只有 8 位，会截断裁判的 16 位冷却增益；新裁判结构体也已删除 `remaining_energy`。建议业务数据替换为：

```c
struct
{
    uint8_t recovery_buff;
    uint16_t cooling_buff;
    uint8_t defence_buff;
    uint8_t vulnerability_buff;
    uint16_t attack_buff;
} __packed__ data;
```

发送时逐字段复制同名 `BuffMusk` 字段，删除 `remaining_energy` 的赋值。

| 字段 | 旧业务偏移 / 大小 | 新业务偏移 / 大小 |
| --- | --- | --- |
| `recovery_buff` | 0 / 1 | 0 / 1 |
| `cooling_buff` | 1 / 1 | **1 / 2** |
| `defence_buff` | 2 / 1 | **3 / 1** |
| `vulnerability_buff` | 3 / 1 | **4 / 1** |
| `attack_buff` | 4 / 2 | **5 / 2** |
| `remaining_energy` | 6 / 1 | 删除 |

该包修改后仍是 7 字节，**不能用包长判断新旧版本**。恢复该包发送之前，必须同步接收端字段定义。冷却增益是直接增加的冷却量，不按百分比解释；其余增益按新协议约定解释。

## 6. 当前保持关闭且不扩展的包

| USB ID | 本轮决定 | 以后启用时的要求 |
| --- | --- | --- |
| `0x04` 事件 | 保留当前占位定义与关闭状态 | 当前函数只更新时间戳，未填写事件业务数据；启用前改为 `uint32_t event_data` + `uint32_t event_data_2`，共 8 字节，并实际赋值 |
| `0x0E` 哨兵反馈 | 保留两个既有字段及关闭状态 | 旧 `sentry_info_2` 位含义按 2027 更新；姿态计时需要 `sentry_info_3` 时再扩展 |

当前 `SendDataSentryInfo_s.data` 的内层结构体没有 `__packed__`，两个字段虽合计 6 字节，ARM GCC 实际给内层结构体分配 **8 字节**，末尾包含 2 字节填充。本轮不把它默认为 6 字节，也不顺手缩短包长；若日后明确这个旧布局，应将尾部两字节作为显式保留位并置零。

## 7. 接收端同步与兼容约定

1. USB 帧头、ID、时间戳、CRC 算法及长度计算方式保持不变。
2. `0x0A` 接收端改为读 6 字节业务数据；可按 `len == 24` 识别旧 20 字节布尔包，按 `len == 10` 识别新 6 字节原始位图包。只有需要过渡兼容时才保留双版本分支，其他长度拒绝。
3. `0x0B` 保留原布局；更新伤害原因枚举解释和重装机器人身份含义即可。
4. `0x06`、`0x09` 保持原长度和槽位；旧英雄坐标改按重装解释，原工程等保留槽不得再作为有效目标数据。
5. `0x0D` 长度相同、偏移不同，应同步切换收发定义，不能靠 `len` 自动识别。当前保持关闭，给双方同步留出空间。
6. 首轮维持现有 4 类包的发送开关和任务调用，不新增上传任务、包 ID、自动版本协商或无需求的字段。实际发送周期及 USB 调度优化不属于本次字段适配。
7. 每个上传包仍按现有 `sizeof` 计算 `len` 和 CRC 覆盖范围；字段变更后重新计算帧头 CRC8，不沿用旧包长对应的帧头校验值。

## 8. 仅在业务需要时增加的上传字段

以下是后续扩展，不属于首轮最小改动：

| 上传包 | 可用的新裁判信息 | 扩展方式 |
| --- | --- | --- |
| `0x06` 血量 | 有符号伤害差、R/B 双前哨、敌方基地、双方控制度 | 保留已有 16 字节业务前缀，新增信息放尾部；为每个新增字段列明偏移与长度，不直接把原前缀换成裁判 24 字节结构体 |
| `0x0B` 本机状态 | `bullet_speed_limit`、`hit_sequence`、`hit_position_x/y` 等 | 有消费者后在现有业务数据尾部追加；弹速为 `float`，命中序号为 `uint16_t`，命中坐标为 `int16_t` |
| `0x04` 事件 | 两个 `uint32_t` 事件位图 | 启用时直接定义为 8 字节业务数据；届时 `len = 12`，完整帧 18 字节 |
| `0x0E` 哨兵反馈 | `uint64_t sentry_info_3` 姿态计时 | 若保留旧 8 字节前缀，尾部追加 8 字节后 D 为 16；若双方明确同时换为紧凑的 4 + 2 + 8 布局，D 为 14。两种布局不能混用，本轮均不实施 |

新裁判字段存在不等于必须立即向上位机上传；有明确使用方后再扩展，有助于维持当前接口和最小改动范围。

## 9. 实施与验收清单

后续实施主要集中在上传头文件及发送函数两个源码文件；若无新增业务，不修改下发控制结构、裁判接收解析或其他任务。

- `0x0A`：业务长度 6，完整帧 16；构造两个状态字段分别置位，确认第二字段 bit 8 不被截断，R/B 前哨、补给区、装配区识别正确。
- `0x0B`：业务长度仍为 29，完整帧 39；偏移 24 的高 4 位来自 `HP_deduction_reason`，后面的发弹量和金币偏移保持不变。
- `0x06`：业务长度仍为 16；重装血量来自 1 号槽、原 2 号槽为 0，红哨兵选 R 前哨、蓝哨兵选 B 前哨；身份未知时为 0。
- `0x09`：业务长度仍为 48；偏移 0/4 是重装，原工程、5 号和尾部保留槽全部为 0，不发生坐标串位。
- `0x0D`：冷却增益输入 300 时按 `uint16_t` 完整传输，业务偏移 1/2 为小端 `0x2C 0x01`；完整帧仍为 17，攻击增益位于业务偏移 5。
- `0x04`、`0x06`、`0x09`、`0x0D`、`0x0E` 保持当前关闭状态；未启用函数体内不再引用已删除的裁判成员。
